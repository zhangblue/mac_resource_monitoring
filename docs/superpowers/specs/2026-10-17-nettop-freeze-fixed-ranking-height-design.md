# nettop 卡死修复与进程排行固定高度设计

## 背景与根因证据

应用加入进程排行后，CPU、内存、上传和下载会在运行一段时间后同时停止刷新。对实际卡住的应用进程采样发现：

- AppKit 主线程停在正常事件循环中，不是界面线程死锁。
- 采样任务长期阻塞在 `NetTopExecution.collect()` 调用的 `Process.waitUntilExit()`。
- 同一时刻系统进程列表中已经没有该应用的 `nettop` 子进程。
- Apple Foundation 文档说明 `waitUntilExit()` 会轮询调用线程的当前 RunLoop。当前实现从 Swift detached task 调用它；子进程已经退出后，该等待仍可能无法返回。

因此，根因是进程终止通知与 detached task 中的同步 `waitUntilExit()` 等待不可靠。由于 `MonitoringEngine` 会等待六项采集全部完成后统一提交，一项进程网络采集永久等待会让所有指标看起来一起卡住。

进程排行不足五项时，当前 `ProcessRankingView` 只创建实际存在的行，等待、不可用和空结果则只创建一行文案，因此四张卡片会随进程数量改变高度。

## 目标

1. `nettop` 正常退出、异常退出、超时、输出超限或任务取消后，采集都必须在有限时间内结束，不得永久阻塞监控循环。
2. 继续直接运行固定的 `/usr/bin/nettop` 和固定参数，不使用 Shell、管理员权限或 Network Extension。
3. stdout 与 stderr 继续并发读取，并保持合计 1 MiB 输出上限。
4. CPU、内存、上传和下载卡片的进程区域始终占据五行高度；不足五项时补空行。
5. 保持同名进程 PID、纯数字数值列、380 pt 两列布局、折线图和菜单栏行为不变。

## 非目标

- 不更换进程网络数据来源。
- 不新增进程历史、搜索、终止进程或固定进程功能。
- 不恢复磁盘读写速率。
- 不改变刷新时间、历史窗口或发布签名方式。

## 方案比较

### 方案 1：异步终止信号 + 有界强制清理（采用）

在启动子进程前设置 `Process.terminationHandler`，通过线程安全的一次性终止闩锁把终止事件转换成 async 等待。采集不再调用 `waitUntilExit()`。

运行器统一拥有 800 ms 超时。超时或取消时先发送正常终止信号；宽限期后若同一个子进程仍在运行，再发送强制终止信号。第一条失败原因保持不变，最终仍等待终止事件、两条管道 EOF 和句柄关闭后返回。

优点是改动集中、保留现有架构并直接消除已观测到的阻塞点。缺点是需要谨慎处理“进程在注册等待前已退出”、多次停止和超时/取消竞争。

### 方案 2：使用 POSIX `waitpid`

直接按 PID 等待子进程。它绕过 Foundation RunLoop，但 Foundation `Process` 也管理同一个子进程，可能与内部回收产生 `ECHILD` 竞争，平台耦合更强，因此不采用。

### 方案 3：把进程网络采集拆成独立刷新循环

总量指标不再等待进程排行。这能进一步隔离故障，但会引入额外缓存、生命周期和快照一致性问题；当前根因可在运行器边界内修复，因此暂不采用。

## 子进程生命周期设计

`NetTopExecution` 在 `process.run()` 前完成以下设置：

1. 创建一次性终止闩锁。
2. 设置 `terminationHandler`，回调只完成该闩锁，不直接操作 UI 或 actor。
3. 配置 stdout/stderr 管道。

启动成功后并发启动 stdout 和 stderr reader，然后异步等待终止闩锁。终止事件到达后，继续等待两个 reader 收到 EOF，最后在唯一收尾路径关闭句柄并生成结果。

运行器只保留一个 800 ms watchdog，移除 provider 层重复的超时竞速。watchdog、显式取消和输出超限都调用同一停止入口：

- 锁内记录第一条失败原因；后续原因不得覆盖。
- 子进程运行时先调用 `terminate()`。
- 经过短宽限期仍运行时，仅对本次运行保存的 PID 发送 `SIGKILL`。
- 正常退出会取消 watchdog；强制结束只作为不响应正常终止时的兜底。

`FoundationNetTopCommandRunner.cancel()` 和 `NetTopProcessProvider.cancel()` 继续等待同一个运行任务完成，因此返回时进程、reader 与句柄均已清理，可立即开始下一轮采集。

## 固定五行布局设计

`ProcessRankingView` 始终创建五个 Grid 行槽位：

- 有真实排行时，按当前顺序填充前五项，其余槽位渲染不可见占位行。
- 等待、暂不可用或暂无活动进程时，第一行显示状态文案，其余四行渲染占位行。
- 占位行使用与真实行相同的字体和行高，但不提供可见文字或辅助功能内容。
- 同名进程仍把 PID 作为不可截断的独立后缀；数值列仍为尾部对齐的等宽数字。

标题、Divider 和详情文案保持原位置。这样四张趋势卡在 0～5 个进程、等待和失败状态下高度一致。

## 错误与隔离

- 正常退出：解析 CSV 并发布排行。
- 非零退出、无效 CSV、超时、超量或启动失败：仅进程网络排行暂不可用；现有总量指标和其他采集继续刷新。
- 取消：完成资源清理，不把旧结果提交到新 generation。
- 正常终止无响应：宽限期后强制结束，仍沿统一收尾路径关闭管道。

## 测试与验收

### 自动化测试

1. 使用一个会触发 `terminationHandler`、但其 `waitUntilExit()` 永不返回或直接失败的受控 Process，验证生产运行器可以完成；该测试在旧实现上必须失败。
2. 验证子进程在 async waiter 注册前立即退出时，终止事件不会丢失。
3. 验证超时、取消和输出超限都等待进程与双管道清理，且取消后可以立即重启。
4. 验证不响应正常终止的进程进入强制结束路径，同时保留最初错误类别。
5. 验证 0、1、3、5 个排行以及等待/不可用状态都生成五个视觉行槽位。
6. 使用 `ImageRenderer` 比较上述状态的视图高度，并继续验证同名长进程 PID 与数值可见。
7. 运行完整 `swift test` 与 `swift build -c release --arch arm64`。

### 本机验收

1. 连续运行至少五分钟，确认菜单栏和详情总量持续更新。
2. 采样运行中不应遗留 `nettop` 子进程。
3. 打开详情面板，确认四张卡片在排行数量变化时高度不变，空余位置表现为空行。
4. 确认折线图、纵轴、水平刻度线、hover、设置页和磁盘容量显示不受影响。

## 已知边界

真实界面视觉验收依赖当前 macOS 菜单栏弹窗能被界面工具访问；若自动界面工具无法连接，必须如实记录并保留真机人工验收项，不得用静态代码检查冒充视觉通过。
